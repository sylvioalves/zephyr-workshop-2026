A placa na sua mesa

Dois núcleos RISC-V
HP até 240 MHz e LP até 20 MHz - por isso o alvo pede /esp32c5/hpcore

Fundamentos

O que é o Zephyr?

Um RTOS

Kernel pequeno com threads, escalonador, timers e primitivas de sincronização.

Um sistema de build

CMake + west + Kconfig + devicetree geram um binário a partir da sua configuração.

Uma árvore de drivers

Mais de mil placas e milhares de periféricos atrás de uma única API portável.

Um ecossistema

Módulos, HALs de fabricantes e blobs de RF, tudo orquestrado pelo west.

Fundamentos

A grande ideia

O mesmo aplicativo roda em muitas placas porque o hardware é descrito em dados, não no código.

Esses dados são o devicetree. É por isso que o mesmo código roda em mais de mil placas - e por que ele não compila quando a placa não descreve o periférico que você pediu.

Fluxo de trabalho · duas surpresas

Duas coisas que quase ninguém sabe

1. Devicetree roda antes do Kconfig

O devicetree gera símbolos DT_HAS_<compat>_ENABLED, e os drivers dependem deles:

config ESP32_TEMP
  depends on DT_HAS_ESPRESSIF_ESP32_TEMP_ENABLED

Ligar o nó no devicetree é o que faz o driver existir para o Kconfig.

2. O Zephyr linka mais de uma vez

Tabelas de interrupção e objetos de kernel só podem ser gerados depois de saber os endereços - e gerá-los muda o binário.

zephyr_pre0.elf   ← gera isr_tables
      ↓
zephyr.elf       ← imagem final

02

Devicetree + Kconfig

A hora difícil - e a mais importante do dia.

Lab 2a · o gancho

Vamos fazer o build falhar

west build -p -b esp32c5_devkitc/esp32c5/hpcore \
  samples/sensor/die_temp_polling
error: '__device_dts_ord_39' undeclared here

Este é o erro mais comum do Zephyr. Ele quer dizer: você pediu um dispositivo que o build não criou.

Lab 2a · por quê

O nó existe... mas está desligado

/* in the SoC devicetree */
coretemp: coretemp@6000e058 {
    compatible = "espressif,esp32-temp";
    status = "disabled";   <-- aqui
};
  • O sensor existe no silício e está descrito no devicetree.
  • Como está disabled, nenhum device é criado - e o código não linka.
Lab 2b · o modelo mental

Fio ou chip? Recurso ligado?

Devicetree

Descreve o hardware: o que existe e como está ligado (pinos, barramentos, endereços).

.dts / .overlay

Kconfig

Seleciona o software: quais subsistemas e drivers compilar.

prj.conf / CONFIG_*

Devicetree diz "o sensor existe". Kconfig diz "compile o driver dele".

Lab 2c · a solução

Ligue o nó com um overlay

/* boards/esp32c5_devkitc_hpcore.overlay */
&coretemp {
    status = "okay";
};
  • Três linhas. Não editamos nada do upstream.
  • O &coretemp referencia um nó que já existe - só mudamos uma propriedade.
Lab 2c · funciona

Mesmo código, agora com o sensor ligado

west build -p -b esp32c5_devkitc/esp32c5/hpcore \
  samples/sensor/die_temp_polling
west flash
west espressif monitor
CPU Die temperature[coretemp]: 34.2 °C
CPU Die temperature[coretemp]: 34.3 °C

Não mudamos uma linha do código do sample. Só descrevemos o hardware.

Lab 2d · a metade Kconfig

Ligue (e desligue) o driver

# prj.conf
CONFIG_SENSOR=y
  • Remova CONFIG_SENSOR, recompile limpo: quebra (driver não compilado).
  • Devicetree disse que existe; Kconfig decide se o driver entra no binário.
Fluxo de trabalho · superpoder

Inspecione o que foi gerado

build/zephyr/zephyr.dts   devicetree final, já mesclado
build/zephyr/.config     Kconfig final, já resolvido
  • "Meu overlay pegou?" → procure o nó em zephyr.dts. Se não está lá, o arquivo não foi lido.
  • "Esse CONFIG ficou ligado?" → procure em .config, não no prj.conf.

Estes dois arquivos resolvem a maioria das dúvidas de devicetree e Kconfig.

Lab 2g · o outro tipo de nó ausente

O LED que a placa tem e o devicetree não descreve

west build -p -b esp32c5_devkitc/esp32c5/hpcore samples/drivers/led/led_strip \
  -- -DCONFIG_SAMPLE_LED_UPDATE_DELAY=350
west flash
  • No Lab 2 o nó existia e estava desligado. Aqui ele não existe: o .dts da placa só declara sw0 e watchdog0.
  • Quem descreve o LED é um overlay do próprio sample, já na árvore: boards/esp32c5_devkitc_hpcore.overlay. Nada para escrever, e compila de primeira - ao contrário do 2a.
  • É um WS2812 endereçável no GPIO27, acionado por I2S + DMA - não é um pino que se liga e desliga.
  • Por isso o blinky continua sem compilar: ele quer um led0 de GPIO, e este LED é um led-strip.
  • O -D depois do -- sobrepõe um Kconfig do sample na hora do build: o default é 50 ms, e sem isso o LED pisca rápido demais.
Fluxo de trabalho · fechando o circuito

De onde vem a macro do erro

/* build/zephyr/include/generated/zephyr/devicetree_generated.h */

/* the alias is just a nickname for the node path */
#define DT_N_ALIAS_die_temp0  DT_N_S_soc_S_coretemp_6000e058

/* every node gets an ordinal - this is the 39 in the error */
#define DT_N_S_soc_S_coretemp_6000e058_ORD  39
  • Todo nó do devicetree ganha um ordinal. O do coretemp é o 39.
  • __device_dts_ord_39 é o objeto device desse nó. O nome do símbolo que faltou no link é só o ordinal com um prefixo.

O número muda de árvore para árvore. O mecanismo, não.

Fluxo de trabalho · fechando o circuito

Do alias ao driver, em duas macros

/* application: samples/sensor/die_temp_polling */
IF_ENABLED(DT_NODE_EXISTS(DT_ALIAS(die_temp0)),
           (DEVICE_DT_GET(DT_ALIAS(die_temp0)),))

/* driver: drivers/sensor/espressif/esp32_temp */
#define DT_DRV_COMPAT espressif_esp32_temp
DT_INST_FOREACH_STATUS_OKAY(ESP32_TEMP_DEFINE);
  • DT_NODE_EXISTS é verdadeiro mesmo com o nó desabilitado: ele só olha se o nó está na árvore. A aplicação segue e pede o device.
  • DT_INST_FOREACH_STATUS_OKAY só percorre nós okay. Com o nó desligado, o driver nunca cria esse device.

A aplicação pede um símbolo que o driver não definiu. É esse o erro do Lab 2a.

De onde tudo isso vem

O hardware descrito em texto

dts/riscv/espressif/esp32c5/esp32c5_common.dtsi              o SoC
    uart0: uart@60000000 {                        rótulo: nome@endereço
        compatible = "espressif,esp32-uart";      qual driver opera isto
        reg = <0x60000000 DT_SIZE_K(4)>;          onde, e quantos bytes
        status = "disabled";                      o SoC descreve, não liga
        interrupts = <UART0_INTR_SOURCE ...>;     qual IRQ ele levanta
        interrupt-parent = <&intc>;              quem trata essa IRQ
        clocks = <&clock ESP32_UART0_MODULE>;    de qual clock depende
    };

boards/espressif/esp32c5_devkitc/esp32c5_devkitc_hpcore.dts  a placa
    &uart0 { status = "okay"; };                   a placa liga o nó do SoC
    chosen  { zephyr,console = &uart0; };        papel: quem é o console
    aliases { sw0 = &boot_button; };            apelido: nome fixo → nó
Fluxo de trabalho

O princípio das camadas

Hardware

SoC .dtsi → placa .dts → seu .overlay

Software

defconfig da placa → seu prj.conf → confs extra

Você nunca edita o upstream. Você sobrepõe camadas.

Fluxo de trabalho

Como descobrir o que existe

west build -t menuconfig   # navegar/buscar todos os CONFIG_*
west boards                # listar alvos de placa
  • Bindings de devicetree: a documentação lista cada compatible e suas propriedades.
  • Página da placa nos docs: periféricos suportados e pinagem.
  • Na árvore: dts/bindings/ e samples/ são as melhores referências.
03

Botão, interrupção e log

Entrada por interrupção, não por polling. E logging de verdade.

Lab 3 · conceito

Interrupção > polling · LOG > printk

GPIO por interrupção

Um callback dispara no evento. A CPU não fica presa num laço ocupado esperando o botão.

Subsistema de log

LOG_INF/WRN/ERR: adiado, com níveis, filtrável por módulo. Prefira à printk crua.

Sem um led0 de GPIO na placa, o console é o nosso dispositivo de saída aqui.

Lab 3 · código

O botão de boot já está no devicetree

/* sw0 = boot button, already described by the board */
static const struct gpio_dt_spec button =
    GPIO_DT_SPEC_GET(DT_ALIAS(sw0), gpios);

gpio_pin_interrupt_configure_dt(&button, GPIO_INT_EDGE_TO_ACTIVE);
gpio_init_callback(&button_cb, button_pressed, BIT(button.pin));
gpio_add_callback(button.port, &button_cb);

/* in the callback */
LOG_INF("button pressed (#%u) at %u ms", count, k_uptime_get_32());
04

Threads e semáforo

O modelo de execução do Zephyr, na prática.

Lab 4 · modelo

Threads, prioridade, dormir

  • K_THREAD_DEFINE: pilha, entrada, prioridade - as três coisas essenciais.
  • k_msleep(1000) cede a CPU; não é espera ocupada.
  • Prioridade: número menor = prioridade maior.
  • Veja as threads vivas no shell: kernel thread list.
Lab 4 · regra de ouro

Numa ISR: sinalize e saia

O trabalho lento é da thread, não da interrupção.

O callback do botão só dá k_sem_give(). A thread trabalhadora acorda no k_sem_take() e faz o resto. Esse é o padrão ISR-para-thread.

Lab 4 · código

Semáforo entre ISR e thread

K_SEM_DEFINE(button_sem, 0, 1);

static void worker(void *a, void *b, void *c) {
    while (1) {
        k_sem_take(&button_sem, K_FOREVER);
        LOG_INF("worker woke up from the button ISR");
    }
}
K_THREAD_DEFINE(worker_id, 1024, worker, NULL,NULL,NULL, 5,0,0);

/* in the button callback: just this */
k_sem_give(&button_sem);

Lab 6b · log não é printk

Ligue e desligue log sem recompilar

uart:~$ log status
uart:~$ log disable tempmon     cala esse modulo
uart:~$ log enable dbg tempmon  e agora fala tudo
  • LOG_MODULE_REGISTER(tempmon, ...) dá um nome ao módulo. É esse nome que o shell filtra.
  • Quatro níveis: err, wrn, inf, dbg. Em runtime, por módulo.
  • O runtime só desce até onde a compilação deixou: CONFIG_LOG_DEFAULT_LEVEL define o piso do binário.
  • Num produto: você deixa a instrumentação no código e liga só o módulo sob investigação, na máquina do cliente.

Testes

Você acabou de escrever um app de verdade. Como saber amanhã que ele ainda funciona?

Depois do Lab 6

E amanhã, como você sabe que ainda funciona?

O problema de produto

Uma aplicação real tem várias configurações (com shell, sem shell, com BLE) e roda em mais de uma placa. Testar tudo à mão não escala.

Twister

O runner de testes do próprio Zephyr. Compila e executa N configurações em M plataformas e diz o que quebrou.

  • Você declara o critério de sucesso num sample.yaml ou testcase.yaml, ao lado do código.
  • Com native_sim ele roda sem placa nenhuma - é isso que torna CI viável.
Twister · na prática

O critério de sucesso vira um arquivo

# sample.yaml, ao lado do main.c
common:
  harness: console
  harness_config:
    type: multi_line
    regex:
      - "heartbeat: up for 0 ms"
tests:
  workshop.lab4.threads:
    platform_allow: [native_sim]
west twister \
  -T labs/lab4-threads \
  -p native_sim
1/1 native_sim/native
workshop.lab4.threads
  PASSED (native 3.622s)
  • harness: console casa a saída com regex. Para testes unitários, use ztest.

Levando para o produto

Onde o seu repositório se encaixa

T1O Zephyr é o manifestoÉ o que fizemos hoje: a sua aplicação vive dentro da árvore do Zephyr. Ótimo para aprender. Ruim para produto - o seu código some no próximo west update.
T2A sua aplicação é o manifestoO seu repositório tem o west.yml e importa o Zephyr como projeto. É o padrão de produto: um clone, uma versão fixada, CI reprodutível.
T3FlorestaUm repositório de manifesto separado orquestra várias aplicações e o Zephyr. Para organizações com mais de um produto na mesma base.

Sair do T1 é a primeira decisão de engenharia depois deste workshop.

Levando para o produto · T2

Um west.yml seu

# west.yml na raiz do SEU repositorio
manifest:
  projects:
    - name: zephyr
      url: https://github.com/zephyrproject-rtos/zephyr
      revision: main        # ou v4.4.2 para fixar
      import:
        name-allowlist:    # clone only what you use
          - hal_espressif
  self:
    path: minha-app
  • revision: aceita branch ou tag. main acompanha o upstream; uma tag como v4.4.2 congela, e é o que um produto usa - senão o build de hoje e o de amanhã não são o mesmo build.
  • name-allowlist derruba o clone de ~40 repositórios para os que você usa.
Levando para o produto · T2

O seu repo vira o workspace

west init -m https://github.com/voce/seu-produto ~/ws
cd ~/ws && west update
~/ws/
  .west/        configuração do workspace
  minha-app/    o SEU repositório, com o west.yml
  zephyr/       importado, na revision que você fixou
  modules/      só os do allowlist
  • O seu repositório passa a ser a raiz. O Zephyr vira dependência, não hospedeiro.
  • west update recoloca todo mundo na revisão do manifesto. É o comando da reprodutibilidade.
Levando para o produto

Importar um módulo seu

# 1. no seu west.yml
projects:
  - name: meu_driver
    url: https://github.com/voce/meu-driver
    revision: v1.2.0
    path: modules/meu_driver
# 2. no repo do modulo:
#    zephyr/module.yml
build:
  cmake: .
  kconfig: Kconfig
settings:
  board_root: .
  dts_root: .
  • O zephyr/module.yml é o que transforma um repositório qualquer em módulo Zephyr.
  • settings: com board_root / dts_root / soc_root é como você registra placas e bindings próprios.
  • Para testar rápido, sem mexer no manifesto: -DEXTRA_ZEPHYR_MODULES=/caminho/do/modulo

Bootloader

Antes do seu main() existir, alguém já decidiu qual imagem carregar.

Quem salta para quem

Da ROM até a sua aplicação

  • Dois slots é o que torna OTA seguro: grava no slot livre e volta atrás se a imagem nova não subir.
  • Pegadinha: a placa aponta code-partition = &slot0_partition sempre, mas em simple boot o SoC ignora isso e usa o boot_partition - há um if explícito no CMake do SoC.
Os três casos de build

Simple boot ou MCUboot?

CONFIG_ESP_SIMPLE_BOOT=y
uma imagem só, sem 2º estágio. Liga sozinho quando você não pede MCUboot.
CONFIG_MCUBOOT=y
o que você está compilando é o bootloader.
CONFIG_BOOTLOADER_MCUBOOT=y
é a app que ele vai carregar. Puxa USE_DT_CODE_PARTITION, e é isso que a linka dentro do slot0.
  • O help do próprio Kconfig é explícito: simple boot sobe o sistema com as memórias prontas, mas sem secure boot, sem OTA e sem gestão de slots.
  • O custo é medível: em simple boot a app tem a flash inteira (~8 MB); com MCUboot ela cabe no slot0 e cai para 3840 KB, porque agora moram lá dois slots e o bootloader.
Duas imagens, um comando

Compilando com sysbuild

west build -p -b esp32c5_devkitc/esp32c5/hpcore samples/hello_world --sysbuild
Completed 'mcuboot'
Completed 'hello_world'

build/mcuboot/zephyr/zephyr.bin              35 KB   o bootloader
build/hello_world/zephyr/zephyr.signed.bin  131 KB   a app, assinada
  • Sem --sysbuild sai um binário e o simple boot assume. Com ele saem dois, e o segundo já vem assinado.
  • Você não escreveu nenhum CONFIG_: o sysbuild ligou BOOTLOADER_MCUBOOT e USE_DT_CODE_PARTITION na app sozinho.
  • É o mesmo west flash depois - ele grava as duas imagens, cada uma no seu offset.

A temperatura no seu celular

west build -p -b esp32c5_devkitc/esp32c5/hpcore labs/lab8-ble
west flash && west espressif monitor
<inf> ble_temp: advertising as Espressif-c3d6

Manufacturer data:  FF FF 9D 0D
                    company ID  0x0D9D = 3485 -> 34.85 C
  • Sem conexão e sem pareamento: o dado vive no anúncio, que qualquer scanner lê.
  • O anúncio cabe em 31 bytes, e você monta byte a byte no vetor ad[].
  • Nome = CONFIG_BT_DEVICE_NAME + os 2 últimos bytes do endereço. Ponha o seu no prj.conf: o sufixo separa dois xarás.
  • Fora do chip, byte order importa: sys_cpu_to_le16().

Atualização pelo ar

Trocar o firmware sem tocar na placa - e desfazer se der errado.

Lab 9 · o panorama

O que o Zephyr já tem para OTA

mcumgr / SMP
O mais usado. O grupo img_mgmt recebe a imagem. Transportes: BLE, UART, shell, SPI, UDP e LoRaWAN. Nenhum deles é HTTP.
hawkBit / UpdateHub
Clientes de serviço de gestão de frota. São HTTP, mas falam a API do servidor (a DDI, no hawkBit): você sobe a infra junto.
LwM2M
Objeto 5 de firmware update, com variante _pull. Precisa de um servidor LwM2M.
USB DFU
Funciona e é simples, mas exige cabo. Derrota o "pelo ar".
  • Todos resolvem o mesmo problema, e todos trazem um protocolo de gerência ou um servidor no pacote.
  • O Zephyr já dá as peças soltas: subsys/dfu/img_util escreve no outro slot, subsys/dfu/boot pede a troca e confirma, e http_client baixa.
  • O que não existe upstream é a cola: "pegue esta URL e jogue no slot". São poucas linhas, e ninguém as manteve na árvore. Daí o ota_http ser um módulo externo.
Lab 9 · o manifesto

Trazendo um módulo para o seu projeto

# west.yml na raiz do SEU repositorio
manifest:
  projects:
    - name: zephyr
      url: https://github.com/zephyrproject-rtos/zephyr
      revision: main          # ou v4.4.2 para congelar
      import:
        name-allowlist: [hal_espressif, mcuboot, cmsis, mbedtls]

    - name: zephyr-workshop-2026
      url: https://github.com/sylvioalves/zephyr-workshop-2026
      revision: main
      path: modules/zephyr-workshop-2026
  • Este west.yml é só um exemplo: é assim que o ota_http entraria num projeto seu. No lab de hoje ele entra por EXTRA_ZEPHYR_MODULES, e nada desta tela precisa rodar.
  • O west clona o repositório inteiro no path, e o Zephyr procura zephyr/module.yml na raiz dele.
  • Depois: west init -m <seu-repo> e west update.
Lab 9 · a sala

Quem serve a imagem

# na maquina do instrutor, uma vez
./scripts/publicar-ota.py build/lab9-ota
imagem : build/lab9-ota/zephyr/zephyr.signed.bin
versao : 2.0.0
tamanho: 737452 bytes (720 KB)

na placa, digite:

    ota download http://192.168.0.10:8000/lab9.signed.bin
  • O arquivo é o mesmo zephyr.signed.bin do slide do sysbuild, só republicado com nome curto.
  • O script lê a versão no header do MCUboot antes de servir: você sabe o que está publicando.
  • O servidor é multi-thread, a sala inteira baixa junto. O IP vai no projetor.
  • Placa e servidor na mesma rede, e a porta liberada no firewall: sudo ufw allow 8000/tcp.
Lab 9 · o ciclo

Baixa, testa e volta atrás

uart:~$ ota download http://<servidor>:8000/lab9.signed.bin
  100%  (737452 / 737452 bytes)
uart:~$ ota apply        sem "permanent": entra em teste
uart:~$ ota reboot       sobe a nova
uart:~$ ota status       UNCONFIRMED
uart:~$ ota reboot       sem confirmar -> REVERTE
  • O SSID e a senha vêm do prj.conf: a placa entra na rede sozinha no boot.
  • A imagem vai para o slot que o bootloader não está usando. Só o apply pede a troca.
  • Não confirmar é o caminho da reversão. É isso que torna atualizar em campo seguro.
  • Com ota apply permanent ou ota confirm, a nova fica.
Lab 9 · por dentro

O que o MCUboot faz no swap

1. sobe um setor
Move todos os setores do slot0 uma posição para cima. É por isso que o slot0 precisa de um setor extra.
2. desce o novo
Copia o setor N do slot1 para o setor N do slot0.
3. guarda o velho
Copia o setor N+1 do slot0 para o setor N do slot1. A imagem antiga vai sendo salva enquanto a nova entra.
4. repete
Passos 2 e 3, setor a setor, até o fim. Nenhuma partição de scratch envolvida.
  • Cada passo fica registrado na swap status area: se cair a energia no meio, o bootloader retoma de onde parou.
  • Reverter é o mesmo swap de novo. Não há cópia extra a fazer, e é por isso que não confirmar sai de graça.
  • O preço: imagem-maxima = (N-1) * setor - trailer. Um setor do slot0 nunca guarda código.
  • A doc do MCUboot já prefere swap-using-offset para projeto novo; usamos move por ser o mais rodado em campo.
